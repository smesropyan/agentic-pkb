# The Tree — `T-*` Rules (`DESIGN.md` §1)

**Date**: 2026-08-13
**Status**: Minted. Task 1 of `docs/superpowers/plans/2026-08-13-phase1-the-tree.md`; no code changes
yet. Tasks 2–11 of that plan build `pkb.core` against this contract, one docstring and one test per

**Scope**: `pkb.core` — the mechanical tree layer `DESIGN.md` §1 ("The Tree") specifies. Session
files get frontmatter rules here (§1.3, §1.5) because `DESIGN.md` §1.3 states them; their body and

## 0. How to read this document

`DESIGN.md` §1 is the one source. Where a rule's text is a direct quotation the cell says so with
quotation marks; where it collapses several sentences of prose into one testable assertion the cell
paraphrases and the section heading is the citation. **Rule ids are stable** — a docstring or a test
that implements a rule cites its id (`CLAUDE.md`, "Conventions"), and changing behaviour means
changing the rule here first.

**Severity convention.** For a rule a validator asserts per write (`DESIGN.md` §1.9, "per write"),
severity is the severity of the emitted `Finding`: `error` fails the write, `warning` reports it and
lets the write land. For a rule a generator or a classifier asserts instead — a registry's contents,
the role a path resolves to, a byte-idempotence property — severity states how load-bearing it is:
`error` = must hold or the layer is wrong, `warning` = should hold, and a build that leaves it
unmet needs a written reason.

**The two rulings** the plan records above its task list are minted here rather than left as prose:
P1 (a breadth file's `## Approaches` section, copied verbatim) is **T-38**; P2 (a root `index.md` on
disk is `UNEXPECTED_ROOT_ENTRY` and untouched) is **T-37**.

**Every rule id below is stable and must be referenced in the test that covers it.**

## 1. Rule tables

### 1.1 Standard topic structure

| ID | Rule | Sev | Test assertion |
|----|------|-----|-----------------|
| T-1 | A topic root holds exactly: `topic.md`, `index.md`, `references/` (`summary.md` plus one `[source-name]/` folder per ingested document, each holding `[source-name].md` and `[source-files]`), `notes/` (`summary.md`, standalone `[note-title].md` files, and optional `[note-title]/` folders holding `[note-title].md` plus `media/`), and optionally `skills/`, `expert.md`, and `sub-topics/` — nothing else, because "a topic organizes its content by tag rather than by folder, so every topic has one shape... | T-2 | **Naming convention for folder-hosted items**: "give every item inside its own folder a main file named after it" — `notes/[note-title]/[note-title].md`, `references/[source-name]/[source-name].md` (§1.1, quoted). | T-3 | A nested topic follows the same structure recursively, under `sub-topics/` (a literal directory name), and its parent topic's Topic Expert serves it unless it holds its own `expert.md` (§1.1, §1.8 rule 5). | error | `find_topic_roots` discovers a topic nested under `sub-topics/` with the identical file set as a top-level topic, modulo path prefix; `resolve_expert` walks up past a sub-topic with no `expert.md` to its parent's. |

### 1.2 File types and creation rules

| ID | Rule | Sev | Test assertion |
|----|------|-----|-----------------|
| T-6 | Three approval modes cover the tree: "**Derived** – harness code writes the file, no agent may write it, and nobody approves it. **Approved** – an agent drafts, and the operator reads the exact bytes before the file lands. **On instruction** – the file lands inside the turn on the operator's ask, and that ask is the approval" (§1.2, quoted). The **collaboration rule** draws the line between them: "the practical and procedural pillars are human-generated, AI-curated... Every other meaning-carrying file, `topic.md`, the breadth summaries and a session's synthesis, is AI-generated, human-curated" (§1.2, quoted). | error | The role→mode table `pkb.core` exposes matches DESIGN §1.2 exactly, not merely covers every role: `expert.md` → Approved; a topic `index.md` and the root `tags.md` → Derived; `sessions/*.md` → On instruction then Approved; `references/[source-name]/[source-name].md` → On instruction then Approved; `topic.md`, `references/summary.md`, `notes/summary.md`, `notes/[note-title].md`, and every `skills/*/SKILL.md` (topic-level or root) → Approved. A table that assigns any of these the wrong mode is a defect, not only a table missing a role. |
| T-7 | Two rows carry two modes over one file's life: naming a source is the approval on the first map of it (a later reconciling pass appends inside the turn; a pass that would reword an already-filed argument stops for the operator), and a session's running record needs no approval while its synthesis waits on the operator word for word (§1.2, paraphrased). | warning | `paths.classify` and `validate_content` accept a first-written `references/<src>/<src>.md` (all seven required fields, `source_type: reference`, `type.reference`) with zero findings — Layer 1 checks no separate approval field or gate artifact, which is the mechanical half of "naming the source is the approval". The reword-vs-append distinction over a *later* ingestion pass, and the running-record-vs-synthesis split on a session file, need the turn history Layer 1 does not keep — Phase 2+ scope, not asserted here. |

### 1.3 Metadata and the three file classes

| ID | Rule | Sev | Test assertion |
|----|------|-----|-----------------|
| T-8 | "Three file classes exist" — **1. Knowledge files** (notes, references, the breadth summaries, `topic.md`, session files), **2. Machine-generated files** (a topic's `index.md` at any depth, the root `tags.md`), **3. Skill files** (everything under a `skills/` folder plus `expert.md`) — "and this section governs the first alone" for full PKB frontmatter (§1.3, quoted). | error | `FileRole` partitions into exactly these three classes with no fourth; a role missing from the partition is a defect the classifier test catches. |
| T-9 | Class 1 (knowledge files) carries full PKB frontmatter. A session file is one of these: it sits in the root `sessions/` folder, its `topic` field reads `(session)`, it carries a `topic.*` tag for each expert that took part, it declares no `related_topics`, and the location-agreement check (T-34) "has nothing to compare" — so a session file carrying a running record and no synthesis yet is still a valid knowledge file (§1.3, quoted, paraphrased). | error | `paths.classify("sessions/x.md")` returns `FileRole.SESSION`; validation parses it as a knowledge file but skips `TOPIC_LOCATION_MISMATCH` for it; `topic: "(session)"` is accepted where every other knowledge file would fail `TOPIC_LOCATION_MISMATCH`. |
| T-10 | Class 2 (machine-generated files) carries minimal generated frontmatter only — never `tags`, `created`, `updated`, `related_topics`, and never a `description` (asking a generator to author one "would ask the generators to fail their own validation", §1.3). "The PKB root holds no `index.md`, and the registry is the one derived file above the topics" (§1.3, quoted). | error | A generated `tags.md` parses to exactly `{title, source_type}`; a generated topic `index.md` carries no `tags`/`created`/`updated`/`description` key; a root `index.md` on disk is never written by a generator (T-37). |
| T-11 | Class 3 (skill files) carries no PKB frontmatter, enters no knowledge index, and contributes no tags; a `SKILL.md` carries only the DeepAgent harness's `name` and `description`. `AUTHORSHIP.md`, written by harness code beside a `SKILL.md` (§7.8), "is one of these too", and the catalog generator and the tree walk read only `SKILL.md` inside a skill folder, so `AUTHORSHIP.md` "trips no `LEGACY_SKILL_LAYOUT` warning" (§1.3, quoted). | error | `validate_content` on `skills/voice/SKILL.md` checks only `name`/`description` presence; a `skills/<name>/AUTHORSHIP.md` sibling produces zero `LEGACY_SKILL_LAYOUT` findings and is excluded from the knowledge-file walk. |
| T-12 | Every knowledge file's required frontmatter is exactly the seven fields the canonical example carries: `title`, `description`, `topic`, `tags`, `created`, `updated`, `source_type` (§1.3 example block, lines 152-165). `related_topics` is the **only** recognized optional field — absent, it defaults to empty and is never required. | error | `frontmatter.OPTIONAL_FIELDS == frozenset({"related_topics"})`; `frontmatter.REQUIRED_FIELDS` is exactly the seven named fields; a knowledge file missing any one of the seven is a `MISSING_REQUIRED_FIELD` finding naming it. |
| T-13 | `related_topics` "lists related topic paths in tag notation, such as `bbq.equipment`. The declared value is the bare topic path, and the registry renders it under the `topic.` namespace as `topic.bbq.equipment`... while a value that already carries the namespace stands as written. Declare a cross-topic relationship here and nowhere else" (§1.3, quoted). | error | `normalize_related_topic("bbq")` → `topic.bbq`; `normalize_related_topic("topic.bbq.equipment")` → unchanged (idempotent); no mapping enters the registry (T-26) from any source but `related_topics`. |
| T-14 | A captured source is none of the three file classes. "`[source-files]` beside a map holds the source as it arrived, a PDF, an EPUB, a web page saved as markdown or a text extraction of any of them, and the extension decides nothing: the map is the knowledge file, the source is the material the map reads, and it carries no PKB frontmatter, enters no knowledge index and contributes no tags" (§1.3, quoted). | error | `paths.classify("references/book/scan.pdf")` and `paths.classify("references/book/extract.md")` both return `FileRole.CAPTURED_SOURCE` (never `FileRole.REFERENCE`, which is reserved for `[source-name]/[source-name].md`) with `doc is None`; only `references/book/book.md` classifies `REFERENCE` and is parsed. |

### 1.5 Hierarchical tags

| ID | Rule | Sev | Test assertion |
|----|------|-----|-----------------|
| T-17 | "Three namespaces exist and nothing invents a fourth" (§1.5, quoted): `topic.*` and `domain.*` are open trees the operator grows a branch at a time; `type.*` is a closed set. There is no `status.*` namespace in this design. | error | `{n.value for n in tags.Namespace} == {"topic", "type", "domain"}`; `hasattr(tags, "STATUS_DEFINITIONS")` is `False`; a `status.*` tag on any file is `UNKNOWN_TAG_NAMESPACE`. |
| T-18 | `type.*` is the closed set of exactly four values: `type.note` ("On an observation or an opinion the operator holds from their own practice"), `type.solution` ("On a note recording something that worked and is worth reaching for again"), `type.reference` ("On the map of an ingested source, under `references/`"), `type.summary` ("On `topic.md`, on `notes/summary.md` and `references/summary.md`, and on a session file") (§1.5 table, quoted). | error | `TYPE_TAGS == {"type.note", "type.solution", "type.reference", "type.summary"}`; a fifth value (`type.article`, say) is `UNKNOWN_TYPE_TAG`; the registry's `## Namespace: type` block renders these four static definitions verbatim regardless of KB contents. |
| T-19 | Tag cardinality on a knowledge file: **at least one** `topic.*` tag and **exactly one** `type.*` tag, **tag depth at most 4 levels**, and **a nested tag implies its parent** without needing to be listed — "Every knowledge file carries at least one `topic.*` tag and exactly one `type.*` tag... Keep tag depth to 4 levels or fewer. A nested tag implies its parent. `topic.cooking.grilling` also means `topic.cooking`" (§1.5, quoted). | error | Zero `topic.*` → `MISSING_TOPIC_TAG`; zero `type.*` → `MISSING_TYPE_TAG`; two `type.*` → `MULTIPLE_TYPE_TAGS`; a 5-segment tag → `TAG_DEPTH_EXCEEDED`; a file tagged only `topic.cooking.grilling` renders both nodes in the registry with no "missing ancestor" finding. |
| T-20 | `domain.*` is for "a file whose subject cuts across topics by function rather than by area: `domain.legal.compliance` on a Cooking note about labelling" (§1.5, quoted) — open, unconstrained by file location, checked for syntax and depth only. | warning | `domain.finance.tax` on any topic's file validates with no location lookup; no allowlist exists for `domain.*`. |
| T-21 | Create no ad-hoc tag — "The expert proposes a new tag and the operator approves it before the expert files content that uses it" (§1.5, quoted) — and sessions add no fifth namespace: a session file carries `type.summary` with one `topic.*` tag per expert that took part (§1.5). | warning | `pkb.core` exposes no `approve_tag`/`register_tag` function — tag-vocabulary governance (beyond the closed `type.*` set, T-18) is a Layer 2 session-dialog concern, not a Layer 1 gate; a novel syntactically-valid `topic.*` tag validates clean. |

### 1.6 The tag registry

| ID | Rule | Sev | Test assertion |
|----|------|-----|-----------------|
| T-22 | The root `tags.md` registry is "a complete map... it names every topic the tree holds and a topic cannot be missing from it without being missing from the tree" (§1.6, quoted). The `topic` namespace renders "one section per top-level topic root rather than as a single tree", with sub-topics nesting inside their root's section (§1.6, quoted). | error | Every topic root `find_topic_roots` discovers has a `## Namespace: topic.<root-slug>` section (or is nested under one); the root `tags.md` never omits a topic present in the tree. |
| T-23 | A `topic.*` node's one-line summary is **lifted, never authored**: "A `topic.*` node that a topic folder backs takes the `description` out of that topic's `topic.md`... and gains the marker *(custom expert)* when the topic owns an `expert.md`, so the Librarian never walks the tree to find one" (§1.6, quoted). A `topic.*` node with no folder behind it — a tag inside a topic rather than a topic — "stays bare" (§1.6, quoted). | error | Changing a topic's `topic.md` `description` and regenerating changes exactly the one node line for that topic; `render_root_tags` never invents registry prose; a topic owning `expert.md` renders `CUSTOM_EXPERT_MARKER` on its node and losing `expert.md` removes it; a leaf tag under a topic with no folder behind it renders with no trailing summary. |
| T-24 | `domain.*` "stays bare on purpose. No file sits behind a domain the way `topic.md` sits behind a topic, so a summary would have to be authored and stored somewhere new, and routing turns on topics. The gap is stated rather than filled" (§1.6, quoted). | error | Every `## Namespace: domain` node renders with no trailing summary regardless of KB contents. |
| T-25 | The registry catalogs "the skills the root resolves, the shipped ones and the root's own, from the `name` and `description` in each `SKILL.md`. A topic's own skills stay in that topic's `index.md`" (§1.6, quoted). | error | `render_root_tags(snapshot, shipped_skills=(...))` renders a `## Skills` section from the shipped list plus root `skills/` entries; a topic's own `skills/*/SKILL.md` never appears in the registry, only in that topic's own `index.md` (T-16). |
| T-26 | Cross-topic mappings are "aggregated from the `related_topics` declarations in file frontmatter" (§1.6, §1.9) — from `related_topics` alone, never inferred from shared `domain.*` tags, folder proximity, or prose. | error | Two files sharing a `domain.*` tag with no `related_topics` produce zero mappings; a declared `related_topics` produces exactly the cartesian product of the file's `topic.*` tags and the normalized targets, rendered `` `topic.a` ↔ `topic.b` `` (T-13). |
| T-27 | Registry regeneration is mechanical and byte-idempotent: "Nothing writes a description for the registry, so the registry and the `topic.md` it read cannot disagree... The registry is derived, so it reflects the tags the files use by construction... Regeneration is byte-idempotent, which is what makes it safe to run after every turn" (§1.6, quoted). Siblings sort "case-insensitively by the full tag string, which is what makes regeneration idempotent" (§1.6, quoted). | error | `render_root_tags` called twice on an unchanged snapshot returns byte-identical output; sibling order is independent of on-disk directory iteration order. |

### 1.9 Mechanical maintenance (harness hooks)

| ID | Rule | Sev | Test assertion |
|----|------|-----|-----------------|
| T-33 | Maintenance runs on two clocks: **per write**, in front of the write, so a file that would break the standards never lands; and **once per agent run**, after the turn, over the files that turn touched, bumping their `updated` timestamp with an injected clock and no-op when it already reads today — "Regeneration per write is forbidden, because it would rewrite the root `tags.md` several times in one turn" (§1.9, quoted). No separate maintainer agent exists; Tier 1 is harness hooks no agent can skip, Tier 2 is the Topic Expert's judgment work through overloadable skills, out of Layer 1's scope. Scaffolding a topic runs "on the operator's approval rather than on either clock" (§1.9, quoted), and Tier 1 schedules no conflict work — "The session that made a write runs the check itself, and the report lands in that session" (§1.9, quoted; out of Layer 1 scope, Phase 2). | error | `pkb.core` exposes a per-write `validate_content` and a separate once-per-run `regenerate_all`/`flush`, never a single call that does both; `flush(kb_root, touched_paths=set())` over a populated KB leaves every content file byte-identical; calling `flush` twice in the same turn with the same `touched_paths` is a no-op the second time (T-36); `scaffold_topic` is callable directly and needs no prior flush. |
| T-34 | Per-write validation: "Validate the YAML frontmatter (required fields, tag syntax and depth), the file naming, and the agreement between the declared metadata (`topic`, `source_type`, `topic.*`/`type.*` tags) and the file's location. Validation checks a skill file's placement and never its PKB frontmatter, and a captured source under `[source-files]` passes the same way" (§1.9, quoted). | error | `TOPIC_LOCATION_MISMATCH`, `SOURCE_TYPE_LOCATION_MISMATCH`, and `TYPE_TAG_LOCATION_MISMATCH` each fire for a file whose declared metadata disagrees with its owning topic root or pillar folder; a skill file's placement (topic-level vs. root, `SKILL.md` vs. a legacy flat file) is checked while its absent PKB frontmatter is not; a `CAPTURED_SOURCE` file is never opened for YAML (T-14). |
| T-35 | Once-per-run regeneration duties: regenerate the topic's `index.md` (tag subtree, cross-topic mappings, approach entries — T-38); regenerate the root `tags.md` registry (topic descriptions, `*(custom expert)*` markers, cross-topic mappings — T-22…T-26); regenerate the skills catalog at both levels from each `SKILL.md`'s `name`/`description`, each level listing only what it declared and repeating no other level's (§1.6, §1.9, T-16, T-25); flag broken links and orphaned files (§1.9, paraphrased). | error | A `flush`/`regenerate_all` call over a fixture KB reproduces the golden topic `index.md` files and root `tags.md` byte-for-byte; a topic's skills-catalog entries never repeat a parent topic's or the root's; a dangling link in an approach entry or `related_topics` value is a finding, not a silent drop. |
| T-36 | Every regenerated file is byte-idempotent and deterministic: output does not depend on filesystem iteration order, locale, timezone, wall-clock time, or the absolute KB root path, and carries no timestamp, run id, or file count. | error | Regenerating an unchanged KB writes zero bytes changed on the second call; a fixture regenerated with two different KB-root absolute paths and two different `TZ` values produces byte-identical derived files. |
| T-41 | Tier 1 grows no scan-trigger machinery of its own — "it grows no task queue, no runner and no status field" (§1.8 rule 9, T-32) applies to maintenance's own plumbing, not only to file content: `maintenance.py` exposes no scan-trigger surface, no scan-trigger roles, and no enqueue hook, and its once-per-run regeneration duty (T-35) covers exactly the topic indexes and the registry, nothing else. | error | `hasattr(maintenance, "_SCAN_TRIGGER_ROLES")` is `False`; the module exposes no enqueue-hook function; the public API's per-run regeneration touches exactly the topic `index.md` files and the root `tags.md`, and nothing else. |
